Layout exploration — backlog, later/someday

What piggypal looks like past 900px

Every screen today is designed and built phone-first at roughly a 390px single column — including the bottom-docked entry zone (docs/31). This sketches what actually changes structurally once there's real width to work with, rather than just stretching the same column: does navigation become a persistent rail? does the entry zone move off the bottom dock? do list screens (Transactions, Accounts) split into a list-plus-detail view instead of pushing a new screen? Three directions below, each shown at a desktop width and a tablet width, since the two don't necessarily collapse the same way.

⚠ Nothing here is built. This is the "Custom UI for tablets and desktops" item from docs/00-backlog.md's Later/someday section — flagged, not scoped. None of these directions are decided; picking one (or none — the phone-only build may just stay the shipped experience) is a call for later, and would graduate into its own numbered doc the way every other decision here has.

Direction A

Persistent rail, entry zone moves to the side

Home/Transactions/Accounts/Categories/Insights/Settings become a left-hand rail instead of the app-bar's ▤ icon + kebab. The recent list is untouched — same sunken day-cards, sticky labels, per-day subtotals (docs/33-37) — but the entry zone leaves the bottom dock for a persistent right-hand panel, since position: fixed; bottom: 0 is a mobile-thumb-reach pattern that has no reason to exist once a mouse and a full-height window are available.

Closest analog to a "normal" desktop app shell. Costs two new pieces of chrome (rail, side composer) that don't exist on phone at all — the composer especially needs its own compact idle/preview states designed from scratch, not just docs/22's panel dropped in sideways.

Direction B

List + detail split, answering "does a screen open beside the list, not over it?"

Same rail as A for wayfinding, but the list screens themselves restructure: tapping a Transactions row today pushes /transactions/:id (docs/17) full-screen — here it opens the same edit form beside the list instead, master-detail style, no navigation at all. The composer shrinks to a slim bar above the list column, since the detail pane is now doing most of the work the old bottom-dock preview did.

The most structurally different of the three, and the most work — Transactions, Accounts, and Categories each already have a real full-screen edit form that would need a "does this render inline or as a route" fork, not just a wider container. Worth it mainly if editing-while-scanning-the-list turns out to be a real desktop workflow, which isn't validated yet.

Direction C

Minimal — the phone layout, just centered

No structural change at all: the exact same single component tree as the phone build, bottom-docked entry zone included, just capped at a comfortable reading width (~560px) and centered in whatever window it's given, background filling the rest. The app-bar's ▤ Insights icon and kebab Settings stay exactly as they are — no persistent rail.

Effectively free to build — a max-width wrapper, nothing else changes. Honest cost: it leaves most of a desktop window empty, and a position: fixed; bottom: 0 composer floating in the middle of tall window reads more like an unfinished port than a considered desktop layout. Reasonable as a stopgap if desktop usage turns out to be rare — not as the final answer if it's not.

Not decided

These are three honest structural options, not a recommendation — the backlog item this answers was explicitly "not yet scoped." A is the safest general-purpose desktop shell; B is the most capable but the most work, and depends on desktop editing-while- scanning turning out to be a real workflow; C is nearly free but leaves the desktop window looking like an unfinished port. If one of these gets picked up for real, it should graduate into its own numbered doc the way docs/31–38 did, per docs/00-backlog.md's own convention — reopened deliberately, not by default.
